# V2 规范数据契约

## 1. 目标

V2 只有一套业务主数据。客户、公司、产品不会因为采购、销售、库存、财务或外部平台不同而被拆成多套“看起来相同”的记录。

这里的“一个数据源”指规范业务身份只有一个来源，不等于把所有原始文件抹平到一张表。外部原始记录仍然要保留，用于审计、重放和追溯，但原始记录不能直接充当业务主档。

## 2. 四层数据边界

```text
原始来源证据
    ↓ 只读保存、带来源和指纹
规范主档
    ↓ 稳定内部 ID
业务事实与业务流程
    ↓ 引用规范 ID，可保存历史快照
报表、对账和分析
```

### 2.1 原始来源证据

`source_records` 保存从人工上传、吉客云、1688、银行、税务系统等来源收到的原始内容，至少包含：

- `source_system`：来源系统；
- `source_object_type`：来源对象类型；
- `source_external_id`：来源方编号；
- `received_at`、文件哈希和内容指纹；
- 完整原始行或原始报文；
- 解析状态、错误信息和处理版本。

原始证据不可被后续导入覆盖。重复导入也必须保留原始文件和原始行，只能通过指纹判断是否已经处理过。

### 2.2 规范主体主档

使用一套 `parties` 规范身份，主体类型可以是 `person` 或 `organization`。

客户、供应商、收款方、付款方、自有公司等是 `party_roles`，不是独立的身份表：

```text
parties
  ├── party_roles: customer / supplier / counterparty / own_company
  ├── party_identifiers: 税号、统一社会信用代码、外部客户编号、银行账号等
  ├── party_contacts
  └── party_addresses
```

同一个公司既是客户又是供应商时，只保留一个 `party_id`，增加两个角色。公司专属的法定代表人、税务主体、币种等属性可以放在一对一的 `company_profiles` 中，但 `company_profiles.party_id` 必须唯一，不能成为第二个公司主档。

规范主体至少需要：

- 稳定内部 `party_id`；
- 主体类型和规范名称；
- 规范化名称、税号/统一社会信用代码等可核验身份信息；
- 生命周期状态；
- 创建、修改、合并和停用审计信息。

禁止：

- `customers`、`suppliers`、`companies` 各自保存一份主体身份；
- 各模块只保存名称、不保存 `party_id`；
- 仅凭名称相似自动把两个主体合并。

### 2.3 规范产品主档

产品只有一套规范主档。采购、销售、库存、生产和财务均引用规范 `product_id`，不能分别维护“采购商品”“销售商品”“库存商品”。

一个产品可以拥有规格/变体，但变体必须从属于同一产品聚合，并且所有外部编号都通过映射表关联：

```text
products
  ├── product_variants（如确实存在规格差异）
  ├── product_identifiers（条码、内部编码、平台编码）
  └── product_source_bindings（来源系统对象映射）
```

产品主档必须有稳定内部 `product_id`。`sku`、吉客云 `goods_id`、平台商品编号、条码可以是外部标识或规格标识，但不能替代内部规范 ID，也不能在不同模块重新生成一套商品身份。

## 3. 外部来源映射

所有外部编号进入统一映射关系，而不是散落到各业务表：

```text
external_bindings
  entity_type: party / product / warehouse / channel / company
  entity_id: 规范内部 ID
  source_system: jky / 1688 / bank / tax / manual / ...
  source_object_type
  source_external_id
```

关键唯一性：

- `(source_system, source_object_type, source_external_id)` 必须唯一；
- 一个来源编号只能指向一个规范实体；
- 规范实体可以有多个来源映射，但不能因此复制规范实体；
- 映射不确定时，进入 `needs_review`，不自动写入错误的主档。

## 4. 业务事实引用规则

订单、采购单、入库单、库存流水、发票、银行流水和财务事项都属于业务事实。它们必须引用规范 ID：

- 客户/供应商/公司：`party_id`；
- 产品/规格：`product_id`，必要时加所属变体 ID；
- 仓库：统一 `warehouse_id`；
- 财务主体：统一 `party_id` + 法务/财务属性。

业务事实可以保存“当时显示名称、当时价格、当时税率”等历史快照，这是为了保持历史账实一致，不是重新建立主档。快照字段必须明确标记为 snapshot，不能被页面当成当前主数据编辑。

任何导入器都必须经过同一条流程：

```text
接收原始证据
  → 计算来源指纹
  → 解析标准字段
  → 通过统一匹配器查找规范 ID
  → 已确认则引用规范 ID
  → 不确定则进入待审核
  → 写入业务事实和来源关联
```

导入器不能直接创建自己的客户表、供应商表或商品表。

## 5. 合并、拆分和修改

- 规范 ID 一旦发出不复用、不改含义；
- 同主体合并必须生成审计记录，并把旧 ID 标记为 `merged`，保留指向的新 ID；
- 不能确认是否同主体时，保留两条记录并进入审核，不强行合并；
- 合并后所有业务事实和外部映射必须可追溯到最终规范 ID；
- 删除采用停用/归档，不物理删除已有业务事实或原始证据。

## 6. V2 第一阶段验收标准

第一批主数据代码完成前必须满足：

1. 同一个客户从两个来源导入，只产生一个 `party_id`；
2. 同一个公司同时承担客户和供应商角色，只产生一个 `party_id`；
3. 同一个产品从采购、销售和库存入口写入，只产生一个 `product_id`；
4. 相同名称但无足够证据的两个主体不会被自动合并；
5. 重复导入不会丢失原始文件、原始行或来源指纹；
6. 所有规则都有数据库唯一约束或自动化测试保护。

## 7. 明确不做的事情

- 不把旧系统的 `business_partners`、`suppliers`、`products`、`product_skus` 和各平台商品表原样搬到 V2；
- 不通过复制一份数据来“兼容”每个业务模块；
- 不在没有数据盘点、映射报告和回滚方案前写生产迁移脚本；
- 不把外部平台凭证或原始业务文件提交到公开 Git 仓库。
